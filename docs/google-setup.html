Setup runbook · about 20 minutes · all eight steps doable today

Getting Google Calendar into the app

One Cloud project, one OAuth client, pasted into Supabase, then a page that proves it worked. The whole thing is straightforward except for a single default that will quietly break calendar sync every seven days — so that one is step four, in red.

Do not leave it in Testing

A new OAuth app starts in Testing, and Google expires refresh tokens after seven days for any app in that state asking for more than name and email. Calendar access counts. Left alone, sync works beautifully for a week and then dies, repeatedly, in a way that looks like a bug in our code.

The fix is one button — Publish app — and it does not require Google to verify anything first.

You do not need verification

Calendar is a "sensitive" scope, which normally means a review before you can ship. Google documents an explicit exception for exactly your case: if an app "is used by only a few users, all of whom are known personally to you", verification isn't required. You publish, everyone clicks past one scary-looking screen the first time, and that is the end of it.

The cost is cosmetic: an "unverified app" warning at first sign-in, and a cap of 100 accounts you will never approach.

First

Create the Supabase project before you start, or at least know its reference — the URL looks like https://abcdefgh.supabase.co. Step 5 needs it, and going back to add it later is the usual reason this takes two sittings instead of one.

01

Create the project.

console.cloud.google.com → project picker → New project

Call it something you will recognise in a year. Note the project ID it generates; you rarely need it, but it is annoying to hunt for.

02

Turn on the Calendar API.

APIs & Services → Library → search "Google Calendar API" → Enable

Enabling an API and being allowed to call it are separate things — this is only the first half. The permission comes from the OAuth scope in step 4.

03

Fill in the consent screen.

APIs & Services → OAuth consent screen (newer consoles: Google Auth Platform → Branding)

User type External — "Internal" only exists if you pay for Google Workspace, and a personal Gmail account does not count. App name, your email for support, your email for developer contact. Nothing here is permanent.

04

Add the scope, then publish.

Same screen → Data access / Scopes → Add or remove scopes

https://www.googleapis.com/auth/calendar.readonly

Read-only is genuinely enough — the app displays the family's calendars and plans around them, and asking for write access would mean a harder review for a capability nothing uses.

Then go to Audience and press Publish app. Confirm the status reads In production before you move on. This is the step that stops the seven-day expiry.

05

Create the OAuth client.

APIs & Services → Credentials → Create credentials → OAuth client ID → Web application

This page has three fields that all accept a URL, and only one of them is the right one. Take the extra ten seconds here:

Name A label for your own benefit, shown to nobody. Call it "Family app web". Not a URL.
Authorised JavaScript origins Origins only, no paths. Leave it empty — we do not use the flow that needs it.
Authorised redirect URIs This is the one. Scroll down to it; it sits below the origins box.

Under Authorised redirect URIs, press "Add URI" and paste your Supabase callback — copy it from Supabase's Google provider page rather than typing it:

https://YOUR-PROJECT-REF.supabase.co/auth/v1/callback

Only if you also intend to run Supabase itself locally, add this second one. Skip it if you are using the hosted project:

http://localhost:54321/auth/v1/callback

Then Save. Google can take a few minutes to propagate a change here, so if it still complains immediately, wait and retry before assuming it is wrong.

06

Copy both credentials into Supabase.

Supabase dashboard → Authentication → Sign In / Providers → Google

Turn the provider on, then fill in Client ID and Client Secret — the field may be labelled "Client IDs" in the plural, which is for native apps and takes the same value here. Then press Save; the toggle alone does not persist anything.

Getting the secret in is the step most likely to be missed, because the provider will happily sit there looking enabled without it. If you later see Unsupported provider: missing OAuth secret, this is the screen it means.

07

Tell Supabase where it is allowed to send people afterwards.

Supabase dashboard → Authentication → URL Configuration → Redirect URLs

Google sends the browser back to Supabase, and Supabase then sends it on to your app — but only to addresses on this list. Add the checker page from the next step:

http://localhost:4321/check-google.html

Wildcards work, so http://localhost:4321/** covers local development in one entry. Skip this and the round trip fails at the very last hop, which looks alarmingly like a Google problem and is not one.

08

Prove it works, before writing any of the app.

cd "prototypes/meal-plan" npm run web

Then open http://localhost:4321/check-google.html, paste your Supabase project URL and anon key, and sign in with Google. It runs the real flow and tells you three things: whether you are signed in, whether Google handed back a refresh token, and whether that token can genuinely read your calendar — it lists your next few events to prove it.

The refresh token is the one to watch. Everything else can look perfect while it is quietly absent, and the failure only shows up an hour later when the access token expires with nothing to renew it.

That is the setup finished

The rest is code, and it is not today's job

Below is what the real app will do at sign-in. There is nowhere to put it yet — we have not built the sign-in screen — so it is here for reference rather than action. The checker in step 8 already does exactly this, which is the point of it.

supabase.auth.signInWithOAuth({ provider: 'google', options: { scopes: 'https://www.googleapis.com/auth/calendar.readonly', queryParams: { access_type: 'offline', // ask for a refresh token at all prompt: 'consent', // ask again even if they said yes before }, }, })

Both query parameters earn their place. Without access_type=offline you get an access token that dies in an hour and nothing to renew it with. Without prompt=consent Google returns a refresh token only on the very first authorisation ever — so the second person to sign in, or anyone re-authorising, silently gets none.

And whenever we do build that screen, the very next thing it must do is write provider_refresh_token to a table of ours. Supabase hands it over once, on the redirect, and does not keep it. Miss that moment and calendar sync works only while somebody has the app open, which is a thoroughly confusing bug to meet three weeks later.

What ends up where

Value From Goes to
Client ID Google Cloud → Credentials Supabase → Auth → Google provider
Client secret Google Cloud → Credentials Supabase → Auth → Google provider
Callback URL Supabase project reference Google Cloud → authorised redirect URIs
Calendar scope Consent screen, and the sign-in call Both — they have to agree
Checker page URL Your machine, once the server is running Supabase → Auth → URL Configuration → Redirect URLs
Anon / publishable key Supabase → Project Settings → API The checker page, in your browser
Refresh token The session, at sign-in A table of ours — later, when sign-in exists

When it goes wrong

Symptom Almost always
Worked for a week, then stopped Still in Testing. Publish the app — step 4.
missing OAuth secret Supabase has Google switched on but no Client Secret stored — step 6. Nothing reached Google at all; the credentials there are fine. Paste the secret and press Save.
A page of raw JSON on a supabase.co address Always a Supabase config problem rather than a Google one, because the browser never left Supabase. Read the msg field — it is usually precise.
redirect_uri_mismatch First check the callback is in Authorised redirect URIs and not in the Name box or the JavaScript origins box — all three take a URL and only one counts. If it is in the right box, compare it character by character with Supabase's, and give Google a few minutes to propagate the change.
Bounced back to Supabase, not to the app The app's own URL is missing from Supabase's Redirect URLs allow list — step 7, which is a different list from Google's.
No refresh token in the session Missing access_type=offline, or missing prompt=consent on a repeat authorisation.
invalid_grant on refresh Token revoked, unused for six months, or the seven-day expiry again.
"Google hasn't verified this app" Expected and fine. Advanced → Go to (app name). Once per person.
"Access blocked: app is in testing" Someone signing in who is not a test user, while the app is unpublished. Publishing fixes it for everyone.

Gemini stays separate

The key you already use for meal plans authenticates you to a model. The credential above authenticates a family member to their own calendar. They cannot substitute for each other, and there is no need to move your existing key into this project — one vendor and one bill was the tidiness argument, not one credential.
